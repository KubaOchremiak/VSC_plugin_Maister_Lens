TL;DR

Twenty alternatives across five decision areas: presentation architecture, artifact rendering, data layer & indexing, navigation model, and relationship to Maister's existing dashboard.html.

The recommended spine is a TreeView for navigation plus one reusable webview panel for reading (A2), in-extension markdown rendering with companion HTML re-hosted through asWebviewUri (B2+B3), a two-tier persisted metadata index with lazy body parsing (C2), an activity-first three-surface navigation model (D2), and a reimplementation of the dashboard's visual language over orchestrator-state.yml with dashboard-data.js as an optional fast path (E3+E4).

Areas are genuinely coupled: a tree-only presentation (A1) forecloses rendered reading inside the extension and therefore fails the universal floor; delegating rendering to VS Code's markdown preview (B1) forecloses the GitLens self-sufficiency property.

The two largest cost drivers — full-text search and portfolio aggregation — are both deferrable without breaking the universal floor, which is what makes a credible first release possible.

Key Decisions

  • Five decision areas, chosen area by area — coupling constraints stated explicitly where one choice forecloses another.
  • Evaluated against the Phase 3 universal floor (rendered reading, workflow-type filtering, § 7 summary block) rather than feature counts.
  • Scope guardrails separate a minimum-viable spine from expansive options, treating full-text search and portfolio roll-up as the two deferrable cost peaks.

Open Questions / Risks

  • warningThe GitLens self-sufficiency property is in direct tension with the cheapest rendering options — every low-cost path pushes the user out to VS Code's preview or an external browser.
  • warningWebview CSP forces a rewrite pass over Maister's companions; inline <style> is allowed under a nonce but inline <script> and the dashboard's dynamic <script src> are not — companion reuse is partial, not total.
  • infoPersisted indexes risk staleness across sessions and Maister upgrades; each needs a cheap invalidation key (mtime + size, or a schema version stamp).
  • infoAccessibility diverges sharply by area: TreeView is accessible for free, webviews inherit nothing and must be hand-built to the project's frontend standard.
  • warningPerformance at hundreds of tasks is unvalidated — no alternative here has been benchmarked, and the glob-plus-parse floor cost is unmeasured.

How to read this

Five decision areas, four alternatives each, each with a concrete mechanism (named VS Code APIs), honest pros and cons, and persona impact. The universal floor from Phase 3 is the pass/fail bar throughout: rendered artifact reading (never source), workflow-type filtering, and the § 7 TL;DR / Key Decisions / Risks block surfaced. Personas: Marek (engineering, live monitoring), Ada (business, rendered reading), Irena (delivery lead, portfolio & staleness).

Decision Area A — Presentation Architecture

How the UI is composed from VS Code's surfaces: TreeDataProvider, WebviewViewProvider, WebviewPanel, CustomReadonlyEditorProvider, TextDocumentContentProvider, decorations, status bar, QuickPick.

A1 — Tree-First, Native Editors

One activity-bar container with TreeViews. TreeItem carries ThemeIcon, description for status/staleness, a MarkdownString tooltip holding the § 7 TL;DR, and contextValue for menus. FileDecorationProvider badges verification outcome. Clicks hand off to markdown.showPreview or vscode.open.

Pros
  • Cheapest by a wide margin
  • Accessibility, theming, keyboard nav free and correct
  • Zero CSP surface, fast at hundreds of nodes
  • MarkdownString tooltips cover more of § 7 than expected
Cons
  • Fails the universal floor — every artifact click leaves the extension
  • No decisions table, findings list, or roll-up possible
  • Irena's aggregate has nowhere to live

Personas: Marek adequate · Ada fails · Irena fails

A2 — Tree for Navigation + One Reusable Webview Panel recommended

A1's trees for navigation, filtering and live state; selecting a task reveals a singleton WebviewPanel in ViewColumn.Beside. Navigation inside the panel is postMessage to the host. WebviewPanelSerializer for restore; localResourceRoots scoped to the task dir plus media/.

Pros
  • Meets the universal floor fully
  • Splits work along each surface's strengths
  • Panel beside the terminal matches Marek's journey literally
  • One reused panel — no tab accumulation
  • Best partial-delivery story: the tree alone is already useful
Cons
  • Two UI technologies plus a postMessage protocol
  • Webview a11y is entirely hand-built
  • Theming via --vscode-* vars, tested across light/dark/HC
  • Competes with code editors for screen space

Personas: Marek ✔✔ · Ada ✔✔ · Irena ✔✔

A3 — Webview-View Only

No tree. window.registerWebviewViewProvider renders the entire product — list, filters, live run, reading — as HTML inside the sidebar, escalating to a panel for full-width documents.

Pros
  • Total design control, one technology, one pipeline
  • Filters, facet chips, sparklines are ordinary front-end work
  • Always visible without an editor column
Cons
  • Sidebar is 250–350px; verification reports read badly there
  • Escape-hatch panel reintroduces the split without the tree's benefits
  • Must rebuild keyboard nav, virtualised scrolling, context menus, a11y
  • Views dispose on collapse unless retainContextWhenHidden

Personas: Ada ✔✔ · Irena ✔ · Marek weakest

A4 — Custom Editor Bound to Task Files

CustomReadonlyEditorProvider registered for orchestrator-state.yml via a customEditors filenamePattern; a maister: TextDocumentContentProvider supplies synthetic docs. Tasks become things you open.

Pros
  • Deeply idiomatic: tabs, splits, Quick Open, pinning, history
  • Anyone landing on a state file gets the good view, not raw YAML
  • Virtual docs get find-widget and highlighting free
Cons
  • Hijacks a file users sometimes need raw
  • No always-visible surface — bad for Marek's primary job
  • Portfolio has no file to bind to; model becomes half-consistent
  • Webview costs without the tree's cheap navigation

Personas: a fine complement for all three, a weak spine for any

Recommendation — A2, optionally adopting A4's custom-editor binding later as an entry point rather than a spine.

The floor forces a webview somewhere (A1 cannot render documents); the live-monitoring primary job forces an always-visible surface (A4 cannot guarantee one). A2 satisfies both without rebuilding the tree in HTML (A3's cost), and degrades gracefully.

Coupling: A1 is incompatible with B2/B3/B4 — choosing it forces B1 and accepts failing the floor. A3 and A4 require B2 or B3. E2 requires a webview, ruling out A1.

Decision Area B — Artifact Rendering Strategy

Hard facts: webviews enforce a nonce CSP. Inline <style> passes with style-src 'unsafe-inline'; inline <script> needs a matching nonce; dynamically injected <script src> — what dashboard.html does — is blocked. Local resources need asWebviewUri() under localResourceRoots; sibling links need rewriting or command: URIs.

B1 — Delegate to VS Code's Built-In Rendering

markdown.showPreviewToSide for md; env.openExternal or Simple Browser for companions. The extension renders nothing.

Pros
  • Zero rendering code
  • VS Code's preview is excellent, accessible, theme-correct, honours user md extensions
  • Companions work perfectly in a real browser — they were built for one
Cons
  • Contradicts the GitLens self-sufficiency property
  • Ada's pain answered with "open it in Chrome"
  • No pinned § 7, no breadcrumb, no deep-linking from a decision to an anchor
  • No task context around the document

Personas: Marek adequate · Ada fails in spirit · Irena neutral

B2 — Render Markdown In-Extension recommended spine

Bundle markdown-it + GFM table and task-list plugins (for - [ ]/- [x]/- [~] in implementation-plan.md). Parse, sanitise, rewrite images to asWebviewUri and sibling .md links to command: URIs, post HTML to the webview. CSS against --vscode-* vars and .vscode-light/dark/high-contrast.

Pros
  • § 7 block hoistable into a pinned header card
  • Sibling links become in-panel navigation — the self-sufficiency enabler
  • Anchors allow tree-decision → heading deep links (Irena's journey)
  • Plan checkboxes give real per-step progress free
Cons
  • Re-implements VS Code's preview, worse at the margins (no Mermaid/math/user plugins)
  • Sanitisation and link rewriting are correctness-sensitive
  • Bundle size, cold parse cost, long-doc virtualisation

Personas: all three; primary enabler for Ada

B3 — Re-Host Maister's HTML Companions recommended, layered

For the 13 companion kinds: read, nonce or strip inline scripts, rewrite relative href/src to asWebviewUri or command: URIs, emit a compatible CSP, inject directly or into a sandboxed <iframe srcdoc>.

Pros
  • Reuses real maintained design — breadcrumb, badge header, stat tiles, TL;DR, TOC
  • Severity badges and tiles arrive free
  • Stays correct as Maister evolves its companion style
  • Cheapest route to a rich reading surface
Cons
  • Companions use prefers-color-scheme, not VS Code theme vars — visible theme clash
  • Older tasks carry older styles → inconsistent by task age
  • html_output: false removes companions; B2 fallback mandatory
  • iframe srcdoc isolates styling but blocks scroll/anchor/link interception

Personas: strong for Ada when companions exist; unreliable alone

B4 — Structured Extraction Instead of Rendering

Parse each artifact into a model — § 7 block plus per-kind structures (spec.md sections, plan task groups, verification verdicts, design-context/INDEX.md ID table, work-log.md entries) — and render native components. "Open full document" as escape hatch.

Pros
  • Most product-like: information designed, not transcribed
  • Cross-task aggregation nearly free — Irena's roll-up is a query
  • Decisions/risks search becomes a first-class facet
  • Kilobyte payloads instead of full rendered reports
Cons
  • Maximum coupling to schemas that are prose followed by an LLM
  • Per-kind parsers degrade silently as Maister drifts
  • Unmodelled content becomes invisible — the plugin hides things
  • § 7 exempts work logs, mockups, screenshots → escape hatch mandatory anyway
  • Highest build cost of the four

Personas: Irena ✔✔ · Ada ✔✔ (skim) · Marek risks frustration — he needs reports verbatim

Recommendation — B2 as the spine, B3 for companions where they exist, B4 applied narrowly to the § 7 block only.

Extract and pin § 7 from every markdown artifact (narrow B4 — the one structure guaranteed across workflows); render the body with markdown-it (B2); offer the styled companion via the rewrite pass when it exists (B3). This makes the degraded html_output: false mode the default path rather than a fallback, matching Phase 2's finding that degraded modes are normal. Full B4 is rejected as a spine for schema-coupling risk.

Coupling: B2/B3/B4 all need a webview → foreclose A1. B1 is the only option compatible with A1, at the cost of the floor. B3 becomes nearly free if E2 is chosen — same rewrite machinery.

Decision Area C — Data Layer & Indexing

No registry (discovery is workspace.findFiles('.maister/tasks/*/*/orchestrator-state.yml')); model-authored YAML with confirmed drift; dashboard-data.js is JS not JSON; resume logic can shrink completed_phases; search must span metadata, decisions/risks, full text and structured facets.

C1 — Lazy, In-Memory Only

findFiles on activation, parse nothing. A Map fills on demand; one FileSystemWatcher invalidates. No persistence. Search is metadata-only over whatever is loaded.

Pros
  • Simplest correct thing — no invalidation, no format to version
  • Instant activation at any task count
  • Memory proportional to what was actually opened
Cons
  • Fails success criterion 3 — cannot filter/sort by status, type, verdict or staleness without a full parse anyway
  • Irena's view impossible; no full-text at all
  • First-use latency on every list operation

Personas: Marek adequate (single live task) · Ada and Irena fail

C2 — Two-Tier Index: Eager Metadata, Lazy Bodies, Persisted recommended

Tier 1: parse only cheap fields from each state file, persist as JSON in ExtensionContext.storageUri, each entry stamped with mtime+size; re-stat and re-parse only what changed. Tier 2: artifact bodies parsed on open, LRU-bounded in memory, never persisted. Watcher with create/change/delete handlers, ~250ms debounce to absorb Maister's full-file rewrites.

Pros
  • Portfolio, facets, staleness (now - mtime) and decisions search all work off tier 1
  • Near-instant second-and-later activations — daily-use extension
  • mtime/size is a cheap reliable invalidation key
  • Debouncing handles phase-boundary full rewrites
  • Bounded memory
Cons
  • A cache can go wrong — needs a schema version stamp to discard on upgrade
  • Cold-start tier-1 parse of hundreds of YAMLs must run off the activation path
  • No true full-text over bodies
  • Two cache layers, two lifetimes

Personas: all three; the only option making Irena's portfolio affordable

C3 — Full Inverted Index in the Extension Host

C2 tier 1 plus a background job feeding every markdown artifact into minisearch/lunr/flexsearch, with field boosting so titles and § 7 decisions outrank body prose. Serialised and incrementally updated.

Pros
  • All four search modes with one ranking model — compound queries like type:development + verdict:failed + free text
  • Fuzzy, prefix, ranking, snippets are library features
  • Fully offline, independent of other tooling
Cons
  • criticalLargest single cost item in the design
  • Tens of MB of I/O; serialised index may exceed the source data
  • Incremental correctness is genuinely hard (identity across renames)
  • Resident memory in a shared extension host
  • Duplicates ripgrep, which VS Code already ships and which is faster

Personas: best search for all three; hardest to justify for a first release

C4 — Delegate Full-Text to ripgrep recommended for v1

C2 tier 1 for facets. For free text: either workbench.action.findInFiles scoped by filesToInclude, or spawn the bundled ripgrep against the tasks tree and parse its JSON into the extension's own result list, joining hits to tasks by path.

Pros
  • Near-zero build cost, faster than any JS index
  • No index to build, persist, invalidate or version — always current
  • Path-to-task join is trivial: the layout is the identity
  • Composes with facets: narrow first, grep only survivors
Cons
  • Spawning VS Code's vendored ripgrep is undocumented and platform-variable
  • The supported alternative hands the user to the search panel — breaks self-sufficiency
  • No ranking, fuzzy matching or field boosting; hits land on syntax as often as meaning

Personas: Marek ✔✔ (remembered phrases) · Ada ✔ (she searches by concept)

Recommendation — C2, with C4 as the first-release full-text answer and C3 held as a later upgrade.

C2 is non-negotiable: every requirement above the single-task level needs a metadata index. Facet-first-then-grep makes ripgrep's lack of ranking much less painful because the candidate set is already small. C3 earns its cost only if usage shows people searching the corpus by concept rather than by remembered phrase.

Coupling: C sits behind A and B. D3 requires C2's eager tier 1; D1/D4 tolerate C1. E4 materially cuts tier-1 cold-start cost.

Decision Area D — Navigation Model

How personas move between portfolio, task, phase and artifact, and how affinity, ownership, staleness and verification outcome are exposed.

D1 — One Tree, Grouping Switcher

A single TreeView whose root level is set by a grouping mode in the title menu (menus.view/title + context keys): by type, status, owner, or recency. Non-active facets show as description text and file decorations.

Pros
  • One mental model, one component, minimal chrome
  • Familiar VS Code idiom (SCM, Testing views)
  • Affinity served by defaulting to group-by-type and remembering collapse state
  • Cheap and fully accessible
Cons
  • One dimension at a time; title bars fit ~3 actions
  • Live run and browse compete in the same tree — Marek wants phases expanded, Ada wants a flat recent list
  • Aggregate counts only fit in group labels

Personas: Marek ✔ · Ada ✔ (awkward together) · Irena thin

D2 — Three Surfaces: Now / Browse / Task recommended

Now — compact always-visible view of tasks with recent write activity: phase, elapsed, last decision, artifacts as they land, watcher-driven not polled. Browse — filterable, facetable portfolio list, escalating to the panel for roll-up tiles. Task — the reusable webview panel; the terminal surface and the only place documents render.

Pros
  • Maps one-to-one onto the jobs Phase 2 identified
  • Each surface optimised rather than compromised across three
  • All three personas converge on an identical Task surface — the Phase 3 principle, literally
  • An empty Now is an honest expression of never-assert-what-you-cannot-observe
Cons
  • More chrome, more sidebar real estate, more to explain
  • Now and Browse overlap — a live task appears in both
  • Now is permanently empty for non-runners (Irena) — a third of the UI dead weight
  • More view contributions and more state to sync

Personas: all three with the least compromise; empty-Now mitigable by default collapse

D3 — Portfolio Dashboard as Home

Opens to a webview portfolio: status counts, type distribution, in-flight, stalled, failed verifications, recent completions. Everything is reached by drilling from there.

Pros
  • Strongest orientation story, most immediately impressive
  • Delivers Irena's journey step one directly
  • Aggregate-to-artifact drill-down is the natural gesture
  • Feels like a product, matching the vision's framing
Cons
  • warningInverts the Phase 2 priority — live monitoring becomes a tile
  • Marek wants one task live, not a portfolio
  • Needs C2's full eager index before anything renders — worst cold start
  • Most likely surface to show numbers the data cannot honestly support (constraint 4)

Personas: Irena ✔✔ · Ada ✔ · Marek poorly aligned

D4 — Command-Palette / Quick-Pick Centric

Maister: Go to Task opens a QuickPick with fuzzy matching over the metadata index, detail carrying the § 7 TL;DR and buttons for actions. Maister: Find Decision searches decisions and risks. A minimal tree shows only the live run.

Pros
  • Fastest recall once internalised; very cheap to build
  • Excellent for "that migration from two months ago"
  • Scales to thousands of tasks with no UI work
  • Minimal screen real estate
Cons
  • Discovery-hostile — nothing is browsable
  • Cannot answer Ada's "what is worth reading?"
  • No aggregation, no ambient awareness
  • Suits code-first users; the target audience is explicitly not code-first

Personas: Marek ✔✔ · Ada weak · Irena fails

Recommendation — D2, with D4's Quick Picks added as an accelerator rather than a model.

D2 is the only model respecting the Phase 2 priority ordering while still giving Irena a real aggregation surface, and it embodies the one-identical-reading-experience principle by making Task the single terminal surface. D3's content is not rejected — it becomes a mode of Browse rather than the front door. D4 costs almost nothing on top of C2 and should ship as commands even in v1.

Coupling: D2 and D3 require A2 or A3. D1 and D4 are the only models compatible with A1. D3 requires C2's eager tier 1.

Decision Area E — Relationship to Maister's dashboard.html

615 lines / 32.6 KB, self-contained, copied verbatim into each task root and pinned to the Maister version that created it. Loads data by injecting <script src="dashboard-data.js?t=…"> — blocked by webview CSP — and polls every 5 s. dashboard-data.js is window.MAISTER_DATA = {…};, a lossy projection, absent when html_output: false.

E1 — Ignore It Entirely

Parse orchestrator-state.yml with yaml/js-yaml behind a tolerant adapter normalising the known hazards: semantic vs phase-N keying, options at two nesting levels, clarifications as a list among map siblings, unknown fields preserved.

Pros
  • One source of truth, no lossy projection, no html_output dependence
  • Access to domain blocks the projection flattens away (task_characteristics, breaking_changes, bottleneck_priorities…)
  • Freedom to design for VS Code idioms
Cons
  • Discards good maintained design work; guarantees visual divergence
  • Full YAML parse per task is the expensive tier-1 path
  • Every future dashboard improvement must be re-implemented

E2 — Host the Real dashboard.html

Rewrite pass: replace the dynamic <script src> loader with a nonce'd inline bootstrap receiving MAISTER_DATA by postMessage, nonce remaining scripts, rewrite artifact hrefs to command: URIs, emit a compatible CSP, replace the 5 s poll with watcher pushes.

Pros
  • Perfect fidelity: HERO_MAP, drawers, expanded-state preservation, verification rendering
  • A lot of working UI for a modest rewrite pass
  • Inherits future dashboard improvements automatically
Cons
  • criticalDepends on the internals of a file the extension does not own — breaks silently, no contract
  • Each task holds a different vintage → N structural variants, inconsistent UI by task age
  • Styles via prefers-color-scheme, not VS Code theme vars → clashes with the editor
  • html_output: false removes it; single-task by construction, so it answers one of three surfaces
  • Accessibility unaudited against the project standard

E3 — Reimplement the Visual Language Natively recommended

Treat the dashboard as a design reference, as Phase 2 framed it. Adopt its IA — phase timeline, hero artifacts per type (HERO_MAP equivalent), decisions/risks drawers, verification section, icon_hint → codicon mapping — re-expressed with VS Code theme vars and the project's frontend standards. Source data is the state file.

Pros
  • Keeps the good structural decisions, sheds the file-protocol browser constraints
  • Theme-correct, accessible, consistent across task ages, works with html_output: false
  • Extends naturally to Portfolio and Now, which E2 cannot
  • HERO_MAP is the direct answer to "twenty files with no signal about which matters"
Cons
  • Build cost, plus ongoing drift from Maister's dashboard as it evolves
  • Requires re-making judgement calls (which artifacts are heroes per type) — visibly wrong if missed

E4 — dashboard-data.js Fast Path, YAML Fallback recommended, conditional

Orthogonal data-source choice. Extract the object with a bounded regex from window.MAISTER_DATA = to the trailing ; and JSON.parse it; fall back to a globals-free vm sandbox only if needed, never bare eval. Missing or unparseable → YAML. Both behind one interface.

Pros
  • 3.5 KB near-JSON parses far faster than full state YAML — directly cuts C2 cold start
  • Flatter, already-normalised schema, free of the phase_summaries keying inconsistency
  • Rewritten at every meaningful state change — equivalent freshness for monitoring
Cons
  • Lossy — domain blocks unavailable, so the fallback is not optional
  • Absent entirely under html_output: false
  • Executing model-authored JS, even sandboxed, is a real risk surface
  • Two code paths → a subtle "works on my task" failure class

Recommendation — E3 for presentation, E4 for data acquisition, with E1's tolerant YAML parser as the mandatory foundation beneath both.

E2 is the fastest route to a good-looking task view but fails on three counts that matter more than speed: theme clash every session, per-task version drift, and inability to serve Portfolio and Now. Phase 2 already framed the dashboard as "a design reference, not a droppable asset" — E3 carries that through. Take E4 only with JSON.parse-first extraction and a complete, independently-correct YAML path; if measurement shows YAML parsing is not actually the bottleneck at target scale, drop E4 as unnecessary complexity under the minimal-implementation standard.

Coupling: E2 requires a webview (rules out A1) and shares its whole rewrite machinery with B3. E4 improves C2's cold-start budget. E1's parser is required regardless.

Scope Guardrails

The two largest cost drivers identified across Phases 1–3 are full-text search (four modes at once, hundreds of tasks) and portfolio aggregation (every roll-up computed by globbing and parsing, with no Maister support). Both are deferrable. Neither is in the universal floor.

minimum viable The spine that satisfies the floor

  • A2 tree + one reusable webview panel
  • B2 in-extension markdown rendering, with the § 7 block extracted and pinned (narrow B4)
  • C2 tier 1 only — metadata index, persisted, watcher-invalidated. No full-text.
  • D2's Now and Task surfaces — Browse present as a flat, type-filterable list without facets or roll-up
  • E1 + E3's HERO_MAP idea — tolerant YAML parser plus per-type hero artifacts. No dashboard-data.js fast path.
  • Workflow launching via Terminal.sendText with composed /maister:* commands — cheap, central to two personas

Clears all four success criteria except "recall in seconds," partially cleared via type/status/recency filtering and title matching.

first release The credible increment

  • C4 free-text search, facet-narrowed first. If spawning the vendored ripgrep proves unreliable, ship search over the indexed § 7 blocks only — and state that limitation plainly in the UI.
  • B3 companion re-hosting behind an explicit "styled report" affordance, B2 as default
  • Staleness and verification outcome as tier-1 facets — nearly free once tier 1 exists, and what Irena needs most
  • D4 Quick Picks (Go to Task, Find Decision) — very cheap on top of tier 1, large recall gain
expansive  Defer and justify with usage
  • C3 full inverted index with ranking and fuzzy matching
  • D3's full portfolio dashboard with counts, distributions and drill-down tiles
  • Throughput and duration metrics — depend on model-authored timestamps Phase 3 flagged as possibly missing or malformed in older tasks, and are the easiest place to violate constraint 4
  • E2 hosting the real dashboard — revisit only if E3 drifts badly from Maister's evolving output
  • Git-derived attribution — useful to Irena, but a git log child process per task dir, fails for uncommitted tasks, and attributes to the committer rather than the operator. After the floor is solid.

Explicit non-goals restated

Repository/git change viewing as a browsable surface, any write to task files or orchestrator-state.yml, and answering orchestrator gates from the UI all remain out of scope per Phase 2. No alternative above crosses those lines; anything that appears to (attribution via git) is a data source only.
