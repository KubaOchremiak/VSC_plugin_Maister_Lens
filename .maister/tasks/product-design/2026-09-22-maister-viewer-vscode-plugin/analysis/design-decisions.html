TL;DR

The extension combines sidebar tree views with one reusable webview panel, plus a compact Overview webview view. The sidebar stacks two natively collapsible views, Now and Overview (counts, filters and the task list; Browse merged in at Phase 7), and the panel switches between Task and Dashboard modes.

Task mode hosts each task's own Maister dashboard.html, unmodified in styling, loading its own data natively inside the webview sandbox, with links intercepted for in-panel navigation. Tasks with no hostable dashboard get a minimal native summary instead.

A tolerant orchestrator-state.yml parser powers everything else: Now, Overview, Dashboard mode, and a persisted two-tier index of metadata plus the TL;DR/decision/risk blocks.

Artifacts render in-extension as markdown with the TL;DR block pinned. Maister's styled HTML companions open on request. Full-text search over artifact bodies is deferred.

Key Decisions

  • A2 presentation (tree + reusable webview panel), extended with a sidebar Overview webview view — the floor requires a webview and live monitoring requires an always-visible surface.
  • B2 + B3 + narrow B4 rendering — markdown rendered in-extension by default, § 7 block pinned, companions re-hosted on request; the markdown-only degraded mode is the default path.
  • C2 only for data — persisted metadata index including § 7 blocks, lazy bodies, no full-text search in the first release.
  • D2 + D3 merged navigation — Now and Overview collapsible in the sidebar (Browse merged into Overview at Phase 7); Overview tiles filter its own task list; panel toggles Task ⇆ Dashboard; no Quick Pick accelerators. Every task carries a one-click next action.
  • E2 + E1 — each task's own dashboard.html hosted for the Task view with Maister's styling unmodified; the tolerant YAML parser is the source for every other surface and for the native fallback Task view.

Open Questions / Risks

  • The hosted dashboard themes itself from the OS prefers-color-scheme, not the VS Code theme — a light dashboard can appear in a dark editor (and ignores high-contrast themes).
  • Each task carries the dashboard.html vintage that created it; the rewrite pass must recognise every structural variant present, and an unrecognised variant silently degrades to the native fallback.
  • Two Task views exist (hosted dashboard and native fallback); users must be able to tell which they are seeing and why.
  • The hosted dashboard's accessibility is unaudited against the project's frontend accessibility standard and cannot be fixed without modifying it.
  • Full-text search deferral narrows Phase 2's four requested search modes to three; success criterion 3 ("recall in seconds") is met for titles, metadata and decisions/risks, not for artifact bodies.
  • Three distinct VS Code surface types (TreeView, WebviewView, WebviewPanel) each need their own accessibility and theming work.

1. Selected Approach

Revised at Phase 7 (mockup review)

The Browse tree was merged into Overview, which now also lists the filtered tasks. The sidebar is Now + Overview, with Open Dashboard as a native Overview title-bar action. Launching also became task-contextual: every task carries a next action (Resume · Start development · Continue from research), one click away on its row, task view and dashboard row. See feature-spec § 4 and § 7.2.

The design splits into sidebar navigation and one reading panel, with two data sources that each do what they are best at.

Sidebar — one view container, two stacked, natively collapsible views

ViewSurface typeJobData source
NowTreeViewEvery unfinished task in this working copy (in progress, pending, blocked), newest activity first: current phase, last recorded decision, artifacts as they land, next action. No time cutoff (revised at Phase 7: colleagues' tasks arrive completed, so unfinished tasks are effectively the user's own).YAML parser + FileSystemWatcher
OverviewWebviewViewCounts by status and type, attention tiles, search, and the filtered task list grouped by type (the former Browse), with each task's next-action button. The title-bar action opens Dashboard mode in the panel.Tier-1 index

VS Code persists each user's collapse state per view, so the layout adapts: Marek collapses Overview and lives in Now; Irena keeps Overview expanded; Ada uses Overview tiles as her daily starting point.

Panel — one reusable WebviewPanel, two modes

Task mode

Hosts the task's own dashboard.html. An injected shim adds the CSP nonce to the dashboard's own <script src="dashboard-data.js"> loader, so the data file loads natively inside the webview sandbox (the extension host never parses or evaluates it); watcher-driven refresh signals trigger immediate re-renders; artifact link clicks are intercepted so they navigate within the panel, where the artifact renders.

Refined in Phase 6, feature-spec § 5.3 — originally specified as data fed by postMessage, which would have required parsing a non-JSON JavaScript literal in the extension host.

Artifact rendering (within Task mode)

Markdown rendered in-extension with the § 7 block extracted and pinned as a header card; a "styled report" affordance re-hosts the .html companion where one exists.

Native fallback Task view

For tasks with no hostable dashboard (html_output: false, or an unrecognised dashboard vintage): header, phase list, § 7 decisions and risks, artifact list, all from the YAML parser. Clearly labelled as the fallback.

Dashboard mode

Full-width portfolio roll-up built on the tier-1 index, drilling into Task mode.

2. Decisions by Area

A

Presentation Architecture

A2, extended
ChosenTree views for navigation and live state, one reusable webview panel for reading. Extended during Area D convergence with a compact WebviewView (Overview) in the sidebar.
RationaleThe universal floor (rendered reading) requires a webview somewhere, ruling out A1. The primary job (live monitoring) requires an always-visible surface, ruling out A4 as a spine. A2 meets both without rebuilding tree behaviour in HTML (A3's cost), and degrades gracefully — the trees are useful on their own.
Rejected alternatives (3)
  • A1 — fails the floor
  • A3 — narrow sidebar, rebuilds free tree behaviour
  • A4 — no always-visible surface; may be added later as an extra entry point
B

Artifact Rendering

B2 + B3 + narrow B4
ChosenIn-extension markdown rendering (markdown-it with GFM tables and task-list checkboxes, sanitised, links rewritten) as the default; the § 7 TL;DR / Key Decisions / Open Questions block extracted and pinned as a structured header; the .html companion re-hosted through a CSP rewrite pass on explicit request.
RationaleMakes the markdown-only mode — which html_output: false forces — the default path rather than a fallback. The § 7 block is the one structure guaranteed across every workflow, so extracting only it avoids the schema-coupling risk of full structured extraction.
Rejected alternatives (4)
  • B1 — breaks self-sufficiency
  • B3-first — theme clash and vintage inconsistency as default
  • Full B4 — fragile per-kind parsers that can hide content
  • B2-only — discards Maister's styled reports
C

Data Layer & Indexing

C2 only
ChosenTwo-tier persisted index — eager metadata plus § 7 blocks, lazy artifact bodies. No full-text search over artifact bodies in the first release.
RationaleEvery requirement above single-task level depends on a metadata index; persistence makes daily use near-instant. Deferring full-text avoids both the inverted-index cost (C3) and the unsupported vendored-ripgrep path (C4).
ConsequenceOf Phase 2's four search modes, three ship — task lookup by metadata, decision/risk recall, faceted filtering. Full-text search is deferred.
Rejected for now (3)
  • C1 — fails recall-in-seconds and Irena's portfolio
  • C3 — largest single cost
  • C4 — unsupported binary path or breaks self-sufficiency
D

Navigation Model

D2 + D3 mergeduser-originated
ChosenNow and Overview stacked and natively collapsible in the sidebar (Browse merged into Overview at Phase 7); Overview tiles and search filter Overview's own task list; panel toggles between Task and Dashboard (plus Risks mode, added at Phase 7). No Quick Pick accelerators.
RationaleThe user proposed merging the three-surface model with the portfolio dashboard so the dashboard is revealed on demand rather than being the front door. This resolves D3's core flaw (demoting live monitoring) while giving Irena a real portfolio surface and Ada an at-a-glance starting point. All three personas still converge on the identical Task surface.
Constraint carriedOverview and Dashboard show only observable facts — counts, verdicts, "quiet for N days" — never throughput, durations or "abandoned" in the first release.
Rejected alternatives (3 + Quick Picks)
  • D1 — one dimension at a time; live and browse compete
  • D3 as home — inverts priority
  • D4 as model — discovery-hostile
  • Quick Picks declined for the first release
E

Relationship to dashboard.html

E2 + E1user-originated
ChosenHost each task's own dashboard.html for Task mode, with Maister's styling left unmodified; the tolerant YAML parser (E1) powers Now, Overview, Dashboard mode, Risks mode, the index, and the native fallback Task view.
Sub-decisions
Which copyEach task's own copy — true to what that task's Maister version produced, and automatically follows Maister's evolution.
ThemingLeft as Maister styles it (OS prefers-color-scheme), not mapped to VS Code theme variables.
RationaleMaximum fidelity to Maister's own per-task view, including HERO_MAP, decision/risk drawers and verification rendering, at the cost of a rewrite pass. Shares its rewrite machinery with B3 companion re-hosting.
ConsequenceTasks with no hostable dashboard need a native fallback view built from the YAML parser.
Rejected alternatives (2 + copy options)
  • E3 — reimplementation: build cost and drift
  • E4 — fast path not needed since the index reads YAML directly; model-authored JS risk
  • Bundled pinned copy and latest-from-install alternatives for the copy sub-decision

3. Trade-Offs Accepted

#Trade-offWhat it means
1Theme inconsistencyThe hosted dashboard follows the OS light/dark setting and ignores VS Code theming, including high-contrast.
2Vintage handlingThe rewrite pass must recognise every dashboard.html version present in the repository; unrecognised versions fall back to the native view.
3Two Task viewsThe hosted dashboard and the native fallback coexist; which one is shown must be explicit to the user.
4Unaudited accessibilityIn the hosted dashboard, which cannot be corrected without modifying it.
5No full-text searchOver artifact bodies in the first release.
6Three surface typesIn the sidebar and panel, each needing separate accessibility and theming work.
7No keyboard Quick Pick acceleratorsIn the first release.

4. Coupling Consequences Realised

PairingConsequence

B3 + E2Share one HTML rewrite pass — nonce injection, link rewriting, CSP emission — so the pair is cheaper together than apart.
