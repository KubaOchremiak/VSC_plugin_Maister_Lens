TL;DR

Build the Maister Lens extension exactly as analysis/design-context/feature-spec.md §§ 1–8 describes it, with the amendments A1–A18 taking precedence wherever the two differ.

They close the ten spec gaps and the audit's two criticals: folderUri is the task identity, one consolidated webview message table is the security allowlist, risksMode.ts joins the § 1.4 layout, task-argument commands are hidden from the Command Palette, one shared open-risks function feeds every count, AC13 applies to Maister Lens's own strings only, list-shaped phase_summaries entries have explicit extraction semantics, and every AC names a harness that can actually run it.

Nothing is reusable in this repo — it is greenfield — so "reuse" means Maister's own dashboard.html hosted unmodified, the two real task folders as fixtures, shared webview primitives across the five bundles, and VS Code theme variables as the only design tokens. Runtime dependencies stay yaml + markdown-it; charts are hand-written SVG; the host never parses or evaluates dashboard-data.js.

Tests: mocha unit (no host) + @vscode/test-electron integration on a pinned stable build, AC7/AC9 measured by a non-gating benchmark, a structural DOM pass over generated webview HTML, an explicit manual checklist, and 2–8 focused tests per task group.

Key Decisions

  • feature-spec.md is referenced, not restated — this spec records only the delta, so implementation follows the amendment where the two disagree.
  • Task identity is folderUri everywhere (index keys, persisted entries, PanelLocation, every message payload); relPath survives only for display and composed commands — it collides across multi-root workspaces.
  • One consolidated message table covers all five surfaces in both directions and doubles as the security allowlist; anything absent is dropped and logged.
  • Risks-mode filtering stays in the webview over the full risks payload; only the workflow-type facet round-trips through the shared setFilter.
  • Task-argument launch commands are hidden from the palette — it carries no task context and Quick Picks were declined (D7). They are reachable only from ▶ buttons.
  • One openRisksOf(task) definition (state + artifact § 7 risks, deduplicated) feeds the Now row, the Dashboard KPI and Risks mode, so a count always matches what a click opens.
  • AC13 governs Maister Lens's own strings, which live in one scanned module; Maister's phase names ("Running E2E tests") are constant input, shown verbatim, exempt.
  • Claude Code chain: claude-vscode.editor.open(undefined, prompt) → env.uriScheme-built URI (only when the extension is installed but the command is missing/throws, treated as success) → next target.
  • Every AC names the harness that can actually run it (A16): the host-observable half in the integration suite, the DOM half as structural assertions over generated webview HTML, the remainder explicitly manual — the host cannot assert inside a webview DOM.
  • No chart library, no sanitizer, no status-bar item, no Quick Pick navigation, no writes to any Maister file.

Open Questions / Risks

  • warningThe Claude Code command signature is undocumented (2.1.278) and ignores the prompt when a session is already open — AC11 pre-fill is manual-only plus a mocked executeCommand unit test.
  • warningworkbench.action.chat.open is registered in VS Code 1.138 whether or not Copilot can answer — the one-time caveat notice is the only mitigation.
  • warningenv.openExternal resolves true even when nothing handles the URI, so the Claude URI attempt effectively ends the chain — hence the install gate.
  • warningNode v26.7.0 is very new: esbuild, mocha and @vscode/test-electron must be smoke-tested before any feature code.
  • infoMockup /screen/* links are preview-server leftovers and the "Browse" wording is stale — the spec wins on wording, the mockups on layout.
  • warningThe hosted dashboard depends on asWebviewUri + <base href> tolerating the real loader's ?t=<epoch> cache-buster — AC3 and AC4 both rest on it. De-risked in the first smoke test with a pre-authorised contingency (A18).
  • infoClaude Code 2.1.278 declares engines.vscode: ^1.94.0, above the ^1.90.0 floor, so test:min can never exercise the claudeCode target.
  • infoThe workflow registry is pinned to Maister 2.2.3; newer phases render by raw id with a warning rather than being hidden.

Goal & user stories

Goal. Ship a TypeScript VS Code extension that makes every Maister task in a workspace visible, readable and actionable inside the editor — always rendered, never as source — and puts each task's next /maister:* action one click away.

Marek — engineering contributorWants every unfinished task with current phase, last decision, recent artifacts and open risks in a sidebar tree, so he can see what is being written right now and resume it in one click.
Ada — business-oriented contributorWants to search and filter all tasks from the sidebar and read any artifact rendered, with its TL;DR, decisions and risks pinned.
Irena — delivery leadWants KPI tiles, filter charts and a portfolio-wide list of open risks, to see failed verifications, quiet tasks and unresolved risks in aggregate.
Any contributorWants Maister's own dashboard.html shown unmodified inside the editor with live data, so nothing is lost relative to a browser.
Untrusted-workspace userWants tasks listed and markdown rendered while no model-authored HTML executes and no workflow can be launched.

A6 — AC13 restated resolves gap 6 · I-3

AC13 (amended): No user-facing string authored by Maister Lens contains "running", "waiting", "stalled" or "abandoned".

  • Exempt as constant input: Maister's own phase names and activeForms in model/workflows.ts — e.g. development phase 12 "Run E2E tests" / "Running E2E tests". Displayed verbatim; paraphrasing would break the very honesty rule the AC protects.
  • Also exempt: task data (titles, descriptions, decisions, risks) — user content the extension relays.
  • In scope: every string Maister Lens authors, all in src/strings.ts — view titles, welcome text, tree labels and descriptions, tooltips, accessible labels, banners, notifications, status-bar messages, webview copy, empty states. Webview bundles import the same module.
  • Enforcement — one mechanism only: a mocha test asserts no exported value in src/strings.ts matches /\b(running|waiting|stalled|abandoned)\b/i — the mechanism the Phase-2 gate ratified. The boundary (no user-facing string authored outside strings.ts) is a code-review convention, not a test: a whole-tree literal scan would need a TypeScript AST pass to tell a TreeItem label from a log line, and would be a speculative second mechanism for an AC the first already satisfies.
A7 — Launch chain amends § 7.4 · resolves gap 8 · I-10
  1. Available only if extensions.getExtension('anthropic.claude-code') exists — otherwise skip to the next targetOrder entry.
  2. await ext.activate(), then commands.executeCommand('claude-vscode.editor.open', undefined, prompt). Success ends the chain.
  3. URI fallback, only when step 1 passed but the command is absent from getCommands(true) or threw: env.openExternal(Uri.parse(`${env.uriScheme}://anthropic.claude-code/open?prompt=…`)). Built from env.uriScheme so Insiders and VSCodium work; openExternal cannot report "unhandled", so it is treated as success and ends the chain (documented as a known limitation).
  4. Only a missing extension advances the chain.

Copilot: workbench.action.chat.open({ query, isPartialQuery: !autoSubmit }). The availability check is weak — VS Code 1.138 registers the command regardless — so a one-time notice (tracked in globalState) states that /maister:* runs only if the user's Copilot setup provides Maister's skills, with an Adjust launch order button.

Terminal and clipboard unchanged (§ 7.5 / § 7.4). Every target is try/caught; a throw is logged and the chain advances; clipboard always succeeds. Resume composes /maister:work {relPath} for all five types — not /maister:{type}.

A14 — List-shaped phase_summaries entries: extraction semantics closes audit C1 · extends N9

N9 accepted a list-shaped entry but never said what is extracted from it. N10–N12 read entry.decisions/.risks/.artifacts — keys a list does not have — so a literal implementation contributes zero decisions from the spec's own designated fixture and loses four real decisions silently, breaching § 2's "never silently discarded" contract and corrupting both the Now tree's Last recorded decision child and AC7's decision search.

An entry may take exactly three shapes:

ShapeHandling
Map (§ 2.3 default)Unchanged: summary, decisions, risks, artifacts per N10–N12
ListA heterogeneous item array, classified below. summary is null; the entry key remains the source

A17 — failed_phases, started_phase and auto_fix_attempts are observable corrects § 2.1 · closes W4

§ 2.1 justifies having no failed PhaseStatus by claiming "a phase-level failure is not observable from state". That is factually wrong: both real state files carry orchestrator.failed_phases, and Maister's own dashboard.html renders a failed-phase glyph. started_phase and a populated auto_fix_attempts are likewise observable, and N15 would drop all three without a ParseIssue, contradicting § 2's governing contract.

The behaviour stands; the rationale and the discard do not.

  • Corrected rationale: PhaseStatus has no failed value because a failed phase is not a durable state — Maister retries it, and the field records attempts rather than an outcome the UI could keep asserting. A gap stays not_recorded, still the honest answer.
  • Nothing silently discarded (N15 amended): a non-empty failed_phases or populated auto_fix_attempts records a warning ParseIssue naming the phases.
  • Surfaced as fact, not as a state: the fallback header's parse-issues link and Raw state section state it plainly — "{n} phases recorded as failed: phase-3, phase-7". No new glyph, no new status word, nothing AC13 forbids.
  • started_phase as a cross-check: § 2.4's derivation still decides currentPhaseId; a disagreement records a warning issue with both values — the derivation wins, and the disagreement is visible rather than hidden.
  • A hazard fixture with populated failed_phases and auto_fix_attempts joins the A8 matrix.
A18 — The hosted dashboard's resource-resolution dependency, de-risked first closes W9

R18 and R23 rest on one unverified behaviour: the real loader executes s.src = "dashboard-data.js?t=" + Date.now(), so the webview requests …vscode-cdn.net/<taskFolder>/dashboard-data.js?t=1758…. The spec never stated that the resource resolver tolerates the query component. If it does not, AC3 and AC4 both fail and two of the four panel modes lose their primary path.

  • Stated as a dependency: asWebviewUri + <base href> must resolve a relative src with its query string intact.
  • Moved into the first smoke test, beside the Node 26 check and before any feature code: host the real fixture dashboard.html in a webview and confirm window.MAISTER_DATA is populated with ?t= present.
  • Pre-authorised contingency, so the discovery costs no re-planning: (1) the shim — which already rewrites the node — strips the query before insertion, and live refresh then relies on the refresh message plus the loader serving from disk per request; (2) if resolution fails regardless, recognize() returns 'unrecognized' for every vintage, Task mode degrades to the § 5.4 fallback with its Open dashboard in browser banner, and the loss is recorded in § 8.5.

Reuse vs new

Existing to leverage

The repo contains no source code — package.json, tsconfig.json, src/, test/, .vscode/, .gitignore all absent. Reuse is external and intra-project.

  • Maister's dashboard.html — hosted verbatim in Task mode; its loadData, 5 s polling and aLink behaviour relied on unchanged
  • HERO_MAP (dashboard.html 249–276) — transcribed into model/workflows.ts
  • The two real task folders in this repo — committed fixture snapshots; this one is the N9 list fixture, the product-design one the object-literal dashboard-data.js fixture
  • Webview CSP + nonce patterns from installed 42crunch.vscode-openapi and anthropic.claude-code — read as patterns, no code copied
  • Shared webview primitives (tile, chip, row, summary card) in src/webview/components.ts + media/ CSS — imported by all five bundles, never duplicated

  • yaml, markdown-it — replace hand-rolling YAML flow mappings and CommonMark+GFM

New — and why

  • model/ — no parser exists for Maister state; N1–N15 + A8 drift are specific to this data
  • index/ — the two-tier + persistence design is specific to the performance targets
  • views/ — VS Code providers must be authored per extension
  • panel/ — hosting and message validation are the security core
  • webview/ five bundles + shim — the shim's nonce/appendChild patch has no equivalent
  • launch/launch.ts — the four-target chain and shell quoting are extension-specific
  • strings.ts — A6 needs one scannable location; cheaper than a whole-tree lint rule

Deliberately not built (over-engineering guard): no chart library or wrapper, no HTML sanitizer, no syntax highlighter, no abstraction layer over the VS Code API, no plugin architecture for workflow types beyond the static table, no status-bar item, no Quick Pick navigator, no write path. Every module above has an immediate caller.

Technical approach

Layering, data flow, security and error handling

Layering (bottom-up). model/ → index/ → views/ → panel/ → launch/, with strings.ts and webview/components.ts as leaf modules. Pure logic (parsers, derivation, query, risks, recognize, insertion, link rewrite, quoting, target order, message validation) stays free of the vscode module so it is unit-testable without a host; classes appear only where the API demands providers or the panel singleton. Everything disposable is registered in context.subscriptions.

Data flow. findFiles per folder → parseState → tier-1 Task keyed by folderUri → persisted + published snapshot → Now and Overview render from the snapshot only (views never read files). Opening a task builds tier-2 TaskDetail; a recognized dashboard.html is hosted, otherwise the fallback view renders. The shim routes clicks and window.open into navigate; the host validates every message against A2, then opens Artifact mode, another task, a file or an external URL. Watcher changes update the index and post refresh or re-render the open artifact.

Security posture. Model-authored JavaScript executes only inside a webview under a per-render 32-byte nonce CSP with default-src 'none', with the shim acquiring acquireVsCodeApi() first so no later script gets a messaging handle; the host never parses or evaluates it. Markdown renders with html:false as the sanitization strategy. Every resolved path is containment-checked. execFile without a shell. Untrusted workspaces run no hosted HTML and expose no launch commands.

Error handling. The parser never throws; every parse, stat and summary extraction is individually wrapped so one bad task cannot affect another; a single "Maister Lens" output channel is the sink; notifications only for the three actionable cases (watcher exclude, Copilot caveat, index persistence failing twice).

Risk handled first. The first task group scaffolds the project and proves, before any feature code: esbuild bundling, one mocha test and one @vscode/test-electron launch on Node v26.7.0 — and the A18 resource-resolution check, hosting the real fixture dashboard.html in a webview and confirming window.MAISTER_DATA is populated with the ?t= cache-buster intact. A18 is the higher-value of the two: the toolchain risk costs a dependency swap, the resolution risk costs two panel modes.

Testing approach & standards compliance

2–8 focused tests per implementation task group; verification runs only that group's new tests, not the whole suite. Group focus: scaffold → build+test smoke; model → parser hazard fixtures, summary extraction; index → persistence, invalidation, watcher debounce; views → tree contents, Overview payload shape; panel → message validation, recognize(), the three insertions, link rewriting; launch → target order with mocked availability, next-action derivation, shell quoting; risks → dedup; strings → the A6 scan. Integration runs on pinned stable (test:integration) with an optional 1.90.0 test:min; AC7/AC9 are a benchmark, not a gate. The DOM suite carries the DOM half of AC4, AC5, AC6, AC8, AC14, AC17 and AC18 per A16, with structural assertions; criteria A16 marks Manual are signed-off checklist items, not automation debt.
