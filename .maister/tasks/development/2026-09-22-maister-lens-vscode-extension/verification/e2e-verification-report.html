Verdict: GO WITH CAVEATS

All five webview surfaces render live from their real built bundles with zero implementation console errors, and every structural claim held. Two Minor defects, both in one function of src/webview/fallbackTask.ts: the status glyph the payload carries is never rendered, and the status word is duplicated into an sr-only span a screen reader reads twice. Four Cosmetic findings, none user-blocking. No merge blockers.

Key Decisions

  • No server, no URL. Runtime verification loaded each built bundle's generated HTML over http://localhost with acquireVsCodeApi stubbed and one payload posted — the technique test/dom/harness.ts establishes (A10/A16).
  • HTTP instead of file:// because the Playwright MCP browser blocks the file: protocol; the shell document is otherwise byte-equivalent to the harness's.
  • Colour and theme declared not assessable. Outside the VS Code host every --vscode-* variable falls back, so all captures render near-monochrome. A harness property, not a defect.
  • AC14 confirmed, not re-derived — the DOM suite was re-run (7/7) plus one live spot-probe, per the task brief.

Open Questions / Risks

  • The fallback view's missing status glyph is also an unused FallbackPayload.statusGlyph field — it reads as a dropped glyph() call, not a design choice. Confirm intent before shipping.
  • Nothing here touches the seven unsigned items in manual-checklist.md. The manual halves of AC3, AC4, AC11 and AC14 remain unverified by any agent.

Discrepancies

Critical: none. Major: none.

Minor MIN-1 — the fallback header never renders the status glyph the payload carries

Spec requirementscreen:task-fallback-view mockup header: Status: ◯ In progress. FallbackPayload.statusGlyph is declared at src/webview/fallbackTask.ts:54 and populated at src/panel/panel.ts:1246.
ExpectedAn aria-hidden glyph span before the status word, as dashboardMode.ts:451 and risksMode.ts:360 draw the same value.
ActualfallbackTask.ts:129-134 emits the formatted string plus hidden(payload.statusText) and nothing else. statusGlyph has no reader anywhere in the bundle.
Evidencescreenshots/03-fallback-task-view.png; live DOM read of p.fb-meta
Root cause hypothesisA dropped glyph(payload.statusGlyph) call — the phase rows in the same file use the glyph+word pattern correctly, and the payload field is otherwise dead.
User impactThe fallback view is the one surface where status is not scannable by glyph, so it reads differently from Overview, Dashboard and Risks. Also leaves an unused payload field, which minimal-implementation.md calls debt.
Recommended fixPrepend glyph(payload.statusGlyph) to the status span; or delete statusGlyph and its producer if the omission is deliberate.
WorkaroundNone needed — the status word is present, so no information is lost.

Minor MIN-2 — the fallback header duplicates the visible status word into an sr-only span

Spec requirementstandards/frontend/accessibility.md — hidden text supplements a glyph that carries meaning; it does not repeat visible text.
ExpectedA screen reader announces "Status: In progress" once.
ActualComputed accessible text is "Status: In progress In progress".
EvidenceLive DOM read of p.fb-meta
Root cause hypothesisThe same dropped glyph() call as MIN-1 — hidden() is the correct partner for an aria-hidden glyph and became redundant once the glyph was not drawn.
User impactScreen-reader users hear the status stuttered on every task fallback view.
Recommended fixFixing MIN-1 makes hidden() correct again; otherwise drop the call.
WorkaroundNone needed — content is correct, only repeated.

Cosmetic COS-1 — a visually-hidden span escapes its clipping ancestor and extends the document box by 94 px at 250 px

Spec requirementstandards/frontend/responsive.md; group 5's "0 horizontal overflow at 250 px and 400 px" claim.
ExpecteddocumentElement.scrollWidth === clientWidth at 250 px.
Actual344 vs 250. The offender is the status .sr-only span inside .trow-description; that ancestor is overflow:hidden but position:static, so it is not the containing block for an absolutely-positioned child and does not clip it.
Evidencescreenshots/02-overview-250px.png — the capture is 344 px wide with 94 px of empty space.
Root cause hypothesisThe .sr-only rule uses position:absolute with no offsets, so the span sits at its static position past the truncated text.
User impactNone observed. body is overflow-x:hidden, so no scrollbar appears and the user cannot scroll; only programmatic scrollLeft moves.
Recommended fixAdd left:0; top:0; to .sr-only in media/webview.css, or give .trow-description position:relative.
Workaroundn/a — nothing is user-visible today; the risk is a future layout change turning this into a real scrollbar.

Cosmetic COS-2 — the Risks heading has no singular form: "1 open across 1 tasks"

Spec requirement§ 5.7 item 1 specifies {open} open across {k} tasks verbatim; RISKS.summary (src/strings.ts:331) implements it exactly.
ExpectedGrammatical output for k = 1.
Actual1 open across 1 tasks
Evidencescreenshots/06-risks-mode.png
Root cause hypothesisFaithful implementation of a spec string written for the plural case. The singular pattern exists elsewhere: RISKS.openCountOne, FALLBACK.parseIssuesOne, OVERVIEW.filterCountOne.
User impactA small copy blemish on a headline line, in a workspace with one affected task.
Recommended fixAdd RISKS.summaryOne following the existing …One convention — a spec copy change, not a behaviour change.
WorkaroundNone needed.
