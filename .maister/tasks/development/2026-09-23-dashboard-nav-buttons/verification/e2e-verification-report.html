⚠️ GO WITH CAVEATS

Both back links (FR3 native, FR4 hosted) pass every runtime check: first DOM node, first Tab stop, accessible name, and exactly {type:'openDashboard'} on activation — zero navigate messages. The W2 defensive-styling fix holds against the exact hostile stylesheet it was written for. But it is narrower than it looks: 8 of 9 hostile-CSS vectors probed still neutralise the link, because only 6 properties carry important while width, height, font-size and pointer-events do not. FR1 (sidebar tree view) is not verifiable by this method — it lives in VS Code chrome.

Open Questions / Risks

  • The W2 claim "survives hostile page CSS" is true only for the specific property set defended.
  • width/height sit at normal priority while overflow/max-height are important — an internally inconsistent defence.
  • Removing the inert z-index was correct (inert on position:static), but nothing replaced it, so a page overlay can cover the link.
  • FR1 needs the @vscode/test-electron path or a manual VS Code window.

Discrepancies

Major 5.2 — hostile-CSS resistance is narrower than claimed

FieldDetail
Spec requirementSpec Open Questions — "The injected link must self-style inline and resist inheritance"; the W2 fix's claim that visibility-critical properties are set with important so the link survives hostile page CSS.
ExpectedThe hosted back link remains visible and clickable regardless of the task-authored dashboard's CSS.
Actual8 of 9 probed vectors neutralise the link (§4.8). The defended set covers only display, visibility, opacity, max-height, overflow, float.
Evidencescreenshots/03-hosted-after-hostile-css.png; §4.8 table; Playwright's own click failure.
Root cause hypothesisBUTTON_STYLE/NAV_STYLE in src/webview/shim.ts mark exactly six properties CRITICAL — a set copied from the W2 review note rather than derived from the properties that can actually suppress an element. Notably ['width','auto'] and ['height','auto'] sit at normal priority right next to overflow at important.
User impactLow in practice, high in principle. Maister's own dashboard has no such rules, so the shipped experience is fine. The exposure is a task-authored dashboard whose CSS collides — that user loses their only way back from the hosted page.
Recommended fixPromote width, height, min-width, min-height, font-size, pointer-events, transform, clip-path, content-visibility and position to important. For overlay resistance add position:relative!important plus a high z-index!important — z-index only takes effect once the element is positioned.
WorkaroundReopen the dashboard from the sidebar "Overview" → "Dashboard" row (FR1) or the command palette.

Minor 5.3.2 — nothing replaced the removed z-index

FieldDetail

Conclusion

⚠️ GO WITH CAVEATS

Both back links do exactly what FR3 and FR4 require — correct structure, first position, first tab stop, accessible names, keyboard operation, and precisely one openDashboard message with zero navigate leakage — verified live rather than inferred, and the W2 fix genuinely defeats the hostile stylesheet it was written against. The caveat is that its defence is narrower than its claim: eight further hostile-CSS vectors still neutralise the hosted link, and no test guards against any of them. Recommend merge, with §5.2 tracked as a fast follow-up plus a regression test that injects hostile CSS — and FR1's sidebar view confirmed separately through the integration harness or a manual VS Code window, since no browser can reach it.
