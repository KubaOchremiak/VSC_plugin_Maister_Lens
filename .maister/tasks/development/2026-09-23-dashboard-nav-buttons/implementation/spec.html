TL;DR

Two navigation affordances over host plumbing that already works. A new first-position tree view titled "Overview" holds one icon-bearing "Dashboard" row that runs the existing maister.openDashboard command; the existing maister.overview webview view is retitled "Tasks" to resolve the title collision. An unconditional "← Dashboard" back link is added at the top of both task renderers — native (fallbackTask.ts, via the existing .link class) and hosted (shim.ts, inline-styled, with hostDashboard.ts untouched). No new command, message type, CSP surface or webview bundle.

Key Decisions

  • New nav view is a tree, not a webview — no new bundle, no sixth DOM surface, VS Code provides keyboard/screen-reader access for free.
  • Existing maister.overview retitled "Overview" → "Tasks" — the new nav section takes the requested "Overview" title, and "Tasks" describes a task list more accurately.
  • The "Project" entry is deferred to a follow-up task — no destination exists, and a stub violates minimal-implementation.md.
  • The hosted back link is injected from src/webview/shim.ts, never from hostDashboard.ts — its "exactly three insertions, all security plumbing" invariant is preserved verbatim.
  • The back link is unconditional in both renderers, mirroring the risks breadcrumb; origin tracking would require new PanelLocation state for no user-visible gain.
  • Copy lives in new FALLBACK.breadcrumb / breadcrumbLabel keys, reused by both renderers.

Open Questions / Risks

  • critical The hosted dashboard.html does not load media/webview.css and carries arbitrary task-author CSS. The injected link must self-style inline and resist inheritance; visual consistency cannot be guaranteed by any test.
  • warning shim.ts stops being a pure messaging bridge and begins injecting one host-owned chrome element. Its header doc comment must be updated or it becomes stale documentation.
  • warning Three test files encode literal counts (nine palette-visible commands, navigation@1/@2, five DOM surfaces). The chosen design keeps both counts unchanged.
  • info The deferred "Project" page remains an open design item for a future task.

Acceptance criteria, per requirement

FR1 — New sidebar navigation view

  1. contributes.views.maister lists exactly three entries in order: nav view (type: "tree", name: "Overview"), maister.now, maister.overview.
  2. A new src/views/navTree.ts exports the view id, a TreeDataProvider with one root node, and a register… factory returning { provider, view, dispose() } — mirroring registerNowTree (nowTree.ts:401-425).
  3. The row: label "Dashboard" from strings.ts, iconPath = new vscode.ThemeIcon('dashboard'), collapsibleState: None, an accessibilityInformation.label, and item.command = { command: 'maister.openDashboard', … }.
  4. getChildren(node) returns [] for any non-root argument.
  5. Registered in src/extension.ts alongside registerNowTree; disposable pushed to context.subscriptions.
  6. No new command, no new palette entry — PALETTE_VISIBLE_COMMANDS stays at nine.
  7. No viewsWelcome entry — the view is never empty.
  8. Never gated on workspace trust (the Dashboard command is not trust-gated, messages.ts:81).

FR2 — Rename the existing Overview view

  1. maister.overview has "name": "Tasks".
  2. OVERVIEW.title (strings.ts:138) value becomes 'Tasks'; key name, view id, provider and view/title entries (openDashboard @navigation@1, openRisks @navigation@2) unchanged.
  3. Its two consumers — <title> and <main aria-label> at overviewView.ts:535,538 — pick it up with no code change; test/dom/harness.ts:56 follows automatically.
  4. No when-clause, context key or view == selector string changes.

FR3 — Back link in the native task view

  1. Structure mirrors risksMode.ts:429-433 exactly: el('nav', {'aria-label': FALLBACK.breadcrumbLabel}, [crumb]) around el('button', {class:'link', type:'button'}, [FALLBACK.breadcrumb]).
  2. Click handler uses the existing local post helper (fallbackTask.ts:75-77) — no new acquireVsCodeApi(), no new post.
  3. The <nav> is the first node appended, before banner(payload) — so also first in tab order.
  4. Rendered unconditionally on every payload; no origin or condition check.
  5. No inline style attribute — the native CSP (panel.ts:1305) omits 'unsafe-inline' for styles. Styling comes solely from .link (media/webview.css:260-275); no new CSS rule.
  6. Accessible name from text content; no positive tabindex; a button, not a heading — the risksSection() heading-as-button pattern (fallbackTask.ts:85-91) is an existing anti-pattern and is not copied.

FR4 — Back link in the hosted task view

  1. <nav aria-label> containing a <button type="button"> reading FALLBACK.breadcrumb, imported from strings.ts — no inline literal.
  2. Inserted as first child of document.body once the DOM is available (guard on document.readyState, else DOMContentLoaded), so it survives the dashboard's own later rendering.
  3. Click posts {type:'openDashboard'} through the existing vscodeApi handle (shim.ts:20) — one acquireVsCodeApi() per page is the hard limit; no new message type.
  4. Carries a distinctive class (e.g. maister-lens-back) and inline style properties for every visual property it depends on (display, flow position, margin/padding, font, color, background, border, cursor, z-index, visibility). Set as properties on element.style, never as a markup string.
  5. Handler attached directly to the button and calls stopPropagation(), so the shim's capture-phase interceptLink never converts it into a navigate message.
  6. The shim's header doc comment (shim.ts:1-6) is updated to state it now also injects exactly one host-owned chrome element.
  7. hostDashboard.ts has a zero-line diff; its "exactly three insertions" contract (:4-12) is preserved.

FR5 — Strings

  1. FALLBACK (strings.ts:226-258) gains breadcrumb: '← Dashboard' and breadcrumbLabel: 'Breadcrumb', mirroring RISKS (:329-330), at the top of the block to match render order.
  2. The nav row's label and accessible name live in strings.ts — a small new NAV block or reuse of an existing key; no literal in src/views/.
  3. No user-facing literal in fallbackTask.ts, shim.ts or navTree.ts (manifest view titles are necessarily literal in package.json).
  4. New strings avoid the wording strings.test.ts forbids (running|waiting|stalled|abandoned).

User Stories

Sidebar reachability

As a developer monitoring Maister state, I want a labelled "Dashboard" row at the top of the Maister Lens sidebar, so that I can open the dashboard without hunting for an unlabelled codicon in a view title bar.

Return from a task

As a developer who drilled into a task from the dashboard, I want a "← Dashboard" link at the top of the task view, so that I can return the same way risks mode already lets me.

Renderer parity

As a developer using either task renderer (native fallback or the task's own re-hosted dashboard.html), I want the same back link in both, so that navigation does not depend on which renderer happened to be chosen.

Accessibility Requirements

  • Every new control is a <button> or a tree item — never a <div>, never a heading-as-button.
  • Both back links sit inside a <nav> with an aria-label from FALLBACK.breadcrumbLabel.
  • The tree row sets accessibilityInformation.label (the nowTree.ts convention) so the spoken name is explicit.
  • No positive tabindex anywhere; document order is tab order, and the back link is first.
  • The native link inherits --vscode-textLink-foreground via .link; the hosted link sets color explicitly from a VS Code CSS variable with a literal fallback, since the hosted page's theme variables are not guaranteed.
  • test/dom/surfaces.spec.ts:190-213 enforces tag/name/tabindex rules automatically for the fallbackTask surface.

Technical Depth

Technical approach

Sidebar (FR1/FR2). Manifest-first: reorder/extend contributes.views.maister and retitle maister.overview. The new provider is a stateless TreeDataProvider<NavNode> with one root node and no onDidChangeTreeData firing (the row never changes); registration mirrors registerNowTree, returning a disposable pushed in src/extension.ts. Activation is unchanged — the view is contributed to an existing container. No badge.

Native back link (FR3). Purely additive inside render(): one <nav> prepended to the existing fragment. The webview → host path is untouched; the click reuses the already-validated openDashboard message, which the host turns into a fresh {mode:'dashboard'} push via TaskPanel.show() — the same forward-navigation semantic risks mode already uses, and the same one that survives reload since history is not persisted.

Hosted back link (FR4). The shim is the only extension-owned code executing inside the re-hosted page. It gains a small injectBackLink() step: build the node with document.createElement, set inline style properties defensively, attach a click handler that stops propagation and posts openDashboard, and prepend to document.body once the body exists. Because the page's own script may re-render regions, the link attaches to body (not to any author container) so it is not clobbered. The hosted CSP allows inline styles; the security boundary (hostDashboard.ts, messages.ts) is untouched.

Ordering invariants. Sidebar order becomes nav → Now → Tasks. Task render order becomes nav → banner → header → sections; the back link is therefore also first in tab order in both renderers.

Assumptions
  • The new view id is not asserted outside the manifest test, so the implementer may pick it (e.g. maister.nav) without downstream breakage.
  • src/strings.ts has no imports and is bundle-safe, so shim.ts may import from it without pulling in extension-host code; if bundle size proves a problem, the copy may instead pass through a narrow shim-local constant sourced from strings.ts at build time — the requirement is no hand-written literal.
  • test/integration/overview.test.ts asserts the surface's title/aria-label; if it does not, FR2's test change reduces to a no-op and only the manifest assertion applies.
  • The dashboard codicon is valid as a ThemeIcon id (already used as a command icon in the manifest).
  • Adding a third view to the container does not alter any existing when clause or context key.

Success Criteria

  2. No two sidebar sections share a title.
  3. Every task view — native and hosted — shows "← Dashboard" as its first element and first tab stop; activating it opens the dashboard.
  4. git diff --stat shows zero lines changed in hostDashboard.ts, messages.ts and at panel.ts:1342.
  5. npm test, npm run test:integration and npm run test:dom all pass; surfaces.spec.ts still enumerates five surfaces and manifest.test.ts still asserts nine palette-visible commands.
