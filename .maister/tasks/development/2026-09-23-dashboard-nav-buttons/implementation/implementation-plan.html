TL;DR

Five task groups, 38 steps, ~20 new tests. Group 1 (strings) is the only true prerequisite; Groups 2, 3 and 4 — sidebar nav view, native back link, hosted back link — then run fully in parallel with zero file overlap. Group 5 closes the audit gaps (rename assertion, docs note) and runs the three suites end to end. All host plumbing already exists: no new command, message type, bundle or CSP surface.

Key Decisions

DecisionRationale
Strings extracted into their own first groupsrc/strings.ts is the single file three downstream groups all touch; isolating it removes the only write contention and lets 2/3/4 run concurrently.
Nav-provider test at test/integration/navTree.test.ts, not test/unit/TreeDataProvider/ThemeIcon/createTreeView need the live vscode module (audit W3).
Suite registration is its own step, with a proof-of-execution sub-stepSUITES.trusted in test/integration/index.ts is hard-coded by name; an unregistered file passes green with zero coverage (audit W3).
FR2 rename gets a manifest ↔ strings.ts drift assertionNothing in the repo asserts the literal 'Overview' today (audit W2).
stopPropagation() kept as plain defence-in-depth onlyThe spec's rationale is false: interceptLink bails at src/webview/shim.ts:118-121 unless closest('a[href]') resolves, and the injected element is a <button> under document.body. No comment may repeat it.
No acceptance criterion asserts runtime sidebar ordercontributes.views order governs first-install layout only; VS Code persists each user's arrangement (audit W4). Manifest order is asserted; runtime order is documented instead.

Open Questions / Risks

  • warningExisting users will not see the new "Overview" view first after update. Mitigation is documentation only — README notes the limitation and points at Views: Reset View Locations. Do not force placement programmatically.
  • warningFR4's visual result inside arbitrary task-authored dashboard.html is untestable — no harness re-hosts a third-party dashboard. Defensive inline styling is the only mitigation.
  • infotest/dom/surfaces.spec.ts runs a blanket a11y loop plus a tabOrder check over the first six controls. Prepending a control to fallbackTask shifts indices; Group 3 must re-run npm run test:dom before Group 5 starts.
  • infosrc/strings.ts is touched by Group 1 only. A later group needing a new key must add it in Group 1's step list, or the parallelism guarantee breaks.
